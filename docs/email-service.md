# Почта KT Companion

Реализован первый этап: почта общего аккаунта Tournament System и Studio.
По умолчанию EMAIL_PROVIDER=disabled. Реальная отправка включается отдельно.

## Поведение

- При включённой почте новые регистрации требуют email. Старые аккаунты
  продолжают входить по никнейму и паролю. Почту можно добавить из профиля.
- В Tournament System и Studio можно войти по никнейму или подтверждённой почте.
  Адреса сравниваются без учёта регистра; ожидающий подтверждения адрес для входа не подходит.
- Привязка/смена требует текущий пароль. Подтверждённый адрес остаётся действующим
  до подтверждения нового. Неподтверждённая регистрация не резервирует чужой адрес.
- Подтверждение: одноразовая ссылка на 24 часа, действие только по кнопке.
- Восстановление: подтверждённый адрес, одноразовая ссылка на 30 минут,
  одинаковый ответ 202 для существующих и отсутствующих аккаунтов.
- Сброс завершает все сеансы. Смена пароля из профиля сохраняет текущий сеанс.
  Оба действия отменяют ожидающую смену почты и все ранее выданные ссылки.
- Подтверждённая смена почты завершает сеансы и аннулирует прежние ссылки.
- Письма: подтверждение, восстановление, изменение пароля, запрос смены адреса
  на старую почту, завершённая смена на старую и новую почту. Русский/английский,
  HTML и plain text. Шаблоны: src/email/templates.js.
- Администратор запрашивает восстановление на подтверждённую почту. Временный
  пароль остаётся для старых аккаунтов без почты и при выключенном сервисе.
- Почта доступна только владельцу аккаунта. Она не включается в публичные
  профили, рейтинг, поиск или краткую сессию общей навигации.
- Формы: /account-email.html, ссылка из профиля; «Забыли пароль?» в Tournament
  и Studio. /account-email.html#admin — состояние очереди для владельца платформы.

Письма о турнирах, парингах, результатах, приглашениях и напоминания по времени
относятся к следующему этапу: потребуются подписки, планировщик и отправитель
events. Существующие уведомления внутри сайта работают как прежде.

## Подключение Resend

1. Проверить Resend → Domains → auth.ktcompanion.ru → Verified. Наличие DNS
   не заменяет проверку статуса в Resend. Домен events для этого этапа не нужен.
2. Создать API key с Sending access только для auth.ktcompanion.ru.
3. Выбрать отправителя, например KT Companion <account@auth.ktcompanion.ru>.
   Reply-To — необязательный существующий ящик, который вы читаете.
4. Создать webhook https://ktcompanion.ru/api/email/webhook, события:
   email.sent, email.delivered, email.delivery_delayed, email.failed,
   email.bounced, email.complained, email.suppressed. Сохранить signing secret.
5. Сгенерировать ключ очереди:
   node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
6. Заполнить серверное окружение:

   EMAIL_PROVIDER=resend
   SITE_URL=https://ktcompanion.ru
   RESEND_API_KEY=<sending key>
   RESEND_WEBHOOK_SECRET=<whsec_...>
   EMAIL_OUTBOX_KEY=<64 hex characters>
   EMAIL_FROM=KT Companion <account@auth.ktcompanion.ru>
   EMAIL_REPLY_TO=<существующий ящик, либо пусто>

   COOKIE_SECURE=true при HTTPS. TRUST_PROXY=true только за одним доверенным
   прокси. Для штатного deploy-скрипта редактировать внешний ENV_FILE
   (по умолчанию /app/tgtv-ts.env): он копируется в .env при обновлении.
7. Отключить tracking кликов и открытий в Resend для auth-домена. Шаблоны в
   панели Resend не нужны: приложение отправляет готовые HTML и text.
8. После разрешённого деплоя миграция 042 и worker запускаются автоматически.
   Проверить /api/auth/email-config, затем очередь под владельцем платформы.
9. На собственном адресе проверить подтверждение, восстановление, письмо
   об изменении пароля. Проверить delivered и отсутствие повторов. Delivered
   означает приём сервером получателя, а не прочтение письма.

## Локальная проверка и выключение

EMAIL_PROVIDER=local разрешён только с HOST и SITE_URL на loopback и вне
NODE_ENV=production. Нужны отдельная локальная PostgreSQL и EMAIL_OUTBOX_KEY.
Письма сохраняются в игнорируемый work/email/<id>.json; внешних отправок нет.
Эти файлы содержат рабочие тестовые ссылки: не публиковать work.

EMAIL_PROVIDER=disabled сохраняет прежний вход и регистрацию без почты.
Почтовые операции возвращают 503; worker не работает. Накопленные письма
не отправляются до включения и не переживают свой срок годности.

## Устройство и ограничения

Миграция 042 добавляет отдельную user_email_accounts: email не попадает в
публичные DTO, старые миграции не зависят от новых полей users. Подтверждённый
нормализованный email уникален, pending_email — нет. Адреса сравниваются без
учёта регистра; плюсы и точки не удаляются. Поддерживаются ASCII-адреса;
международный домен нужно передавать в punycode.

Токен содержит 32 случайных байта; email_tokens хранит SHA-256. Повторная
выдача аннулирует прежний токен того же назначения. Ссылки строятся из SITE_URL,
токен находится во fragment, сразу убирается из URL и не пишется в browser
storage. После перезагрузки страницы нужно снова открыть письмо.
GET страницы не потребляет токен.

Операция и email_outbox сохраняются в одной транзакции. Payload зашифрован
AES-256-GCM. Worker использует FOR UPDATE SKIP LOCKED, lease 60 с, timeout
HTTP 15 с. Соединение БД освобождается до отправки. Неизменный payload и один
Idempotency-Key сохраняются при повторах. Не более 9 попыток с backoff от
30 с до 30 мин, окно не более 23 часов от первой попытки и срока письма.
Payload очищается при отправке, отмене и окончательной ошибке.

Webhooks проверяются по исходным байтам, HMAC-SHA256 и времени (допуск 5 минут).
Повторы дедуплицируются по svix-id. События хранятся отдельно: пришедшие до
ответа send не теряются. Bounce/complaint/suppressed блокируют дальнейшую
отправку на хеш адреса. Снятие блокировки — после разбора причины оператором,
включая suppression в Resend. Кнопки массовой повторной отправки нет.

Общие для процессов лимиты: 90 запросов / 15 минут на IP, 1 письмо со ссылкой /
минуту и 5 / час на получателя, 5 смен адреса / час на аккаунт. Сохраняется
limiter входа. Минимальное время успешного запроса восстановления — 350 мс,
вне соединения БД; при перегрузке абсолютное равенство времени не гарантируется.

Очистка раз в час: outbox и webhooks старше 30 дней, токены через 2 дня после
истечения, старые счётчики через день. Suppressions сохраняются до разбора.
EMAIL_OUTBOX_KEY нужно хранить с резервной копией БД. Нельзя просто менять
его при непустой очереди: сначала завершить/отменить задания и ссылки;
для сохранения очереди потребуется отдельное перешифрование.

## Проверки перед live-запуском

Наборы тестов запускаются при слиянии согласно AGENTS.md. При подготовке
5.1.0 выполнены тесты безопасности почты, HTTP-сценариев, обновления схемы 045
и сохранения серверного env. См. [результаты проверки](email-release-validation.md)
и [инструкцию развёртывания](email-production-runbook.md).

Ручные проверки в отдельной локальной базе: регистрация, подтверждение по
кнопке, повтор/истечение ссылки, сброс и отказ старого пароля, завершение
сеансов, смена адреса до/после подтверждения, отсутствие email в публичных API,
подпись и повтор webhook, блокировка после bounce, мобильная форма.
Сбой провайдера и повторы проверены с подменой HTTP-отправки. Настоящая
доставка и webhook Resend проверяются отдельно при включении на сайте.

Документация провайдера:

- https://resend.com/docs/dashboard/emails/idempotency-keys
- https://resend.com/docs/webhooks/verify-webhooks-requests
