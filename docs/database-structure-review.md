# Структура турнирной БД — рефакторинг 30 октября 2026

Проверены исходники миграций и репозиториев. Изменения подготовлены в checkout;
рабочая БД не подключена (`DATABASE_URL` отсутствует), миграции к ней не применялись.

## Что изменено

- **078:** убраны четыре избыточных индекса раундов, столов, командных матчей и
  связей личных игр. Их запросы покрываются индексами UNIQUE-ограничений.
- **079:** добавлен `games.source_slot`. У одиночных и обычных игр он равен 0;
  у командных игр — номеру личной игры, 1–3. Уникальный индекс по
  `(source_type, source_id, source_slot)` исключает повтор источника, сохраняя
  несколько личных игр одного командного матча. Старые слоты восстанавливаются
  из `tournament_team_match_games`; у вызовов заполняется ID источника вызова.
- **079:** составные FK связывают раунд, ростер, участника ростера, стол,
  исходный матч сетки и личную командную игру с нужным турниром/стороной.
  Щит выбирается из своего ростера, меч — из ростера соперника. Источник личной игры
  проверяется в обе стороны, включая последующее изменение игры.
  Старые ограничения из 035/070 валидируются для существующих строк.
- **080:** из `tournament_matches` удалены `result`, `pending_result`, `elo`,
  `submitted_by_user_id`. Эти значения хранятся в `games`.
  Представление `tournament_match_results` сохраняет привычный набор полей
  для репозитория и API; `scoresByParticipantId` вычисляется при чтении.
  Очки турнира, победитель-участник и состояние сетки остаются метаданными матча.

Репозиторий матчей направляет операции с результатом в `games`, а операции с
сеткой — в `tournament_matches`. При чтении используются канонические значения.
Изменения результата напрямую в SQL также проверяются: отложенный триггер
позволяет записать игру и затем метаданные матча в одной транзакции, но запрещает
зафиксировать противоречивого победителя. Проверки блокируют связанную игру,
чтобы параллельная запись не обходила проверку принадлежности.

## Сохранение существующих данных

Перед удалением колонок миграция 080 привязывает уже существующие канонические
игры и создаёт недостающие игры для старых результатов и полноценных активных
пар. Восстанавливаются записи участников, включая отрицательные ключи гостей.
JSON `null`, которым старый код обозначал отсутствие результата, преобразуется
в SQL NULL. Обычный bye без результата не получает фиктивную игру.

Существующий ненулевой результат игры имеет приоритет. Все различающиеся
значения матча вместе с исходной игрой сохраняются в
`tournaments.result_migration_archive` как свидетельство однократного переноса.
Приложение не использует архив как второй источник результата. При отсутствии
канонического значения оно заполняется из старой колонки матча.

Неоднозначные дубли источников, чужие ссылки и несогласованные победители не
исправляются догадками. Миграция завершается ошибкой, её транзакция откатывается,
данные сохраняются. Сначала нужно явно разрешить такой конфликт, затем повторить
обновление. Миграции 079 и 080 — отдельные транзакции: если 080 откатится,
успешная 079 останется применённой. Старую версию приложения после 079 запускать
нельзя: для отката нужны прежний код и восстановление согласованного дампа.

## Резервирование и применение

Исходные изменяемые файлы и предыдущий рабочий diff сохранены в игнорируемом
каталоге `work/database-refactor-backup-20261030-231107`.

Перед применением 079/080 к существующей БД `migrate()` автоматически создаёт
полный PostgreSQL-дамп в custom-формате. Ошибка резервирования останавливает
обновление до начала миграций. Это действует и при запуске приложения, не только
через CLI. Для новой пустой БД дамп не нужен; исключение для тестов ограничено
Node test runner и точным совпадением соединения с `TEST_DATABASE_URL`.

Отдельная команда: `npm run db:backup -- <каталог>`. Нужны совместимые с сервером
`pg_dump` и `pg_restore` в PATH либо пути `PG_DUMP_BIN` / `PG_RESTORE_BIN`.
`DB_BACKUP_DIR` задаёт постоянное хранилище для автоматических копий;
по умолчанию используется игнорируемый `work/backups`. В Docker-образ добавлены
клиентские утилиты PostgreSQL 16 из [репозитория PGDG](https://wiki.postgresql.org/wiki/Apt),
а Compose сохраняет копии мигратора в отдельном постоянном томе `database_backups`.

Каждая копия имеет уникальное имя, оглавление `.toc` и манифест `.json` с SHA-256.
Проверяются оглавление и полное извлечение SQL из архива, включая чтение данных.
Пароль не передаётся в аргументах процесса или манифесте. Это проверка читаемости
дампа; полноценное восстановление в отдельную БД в этой сессии не выполнялось.
Роли PostgreSQL, серверные настройки и внешние файлы не входят в дамп одной БД.

Порядок обновления существующего окружения:

1. Остановить процессы записи старой версии и сохранить прежнюю версию кода.
2. Настроить соединение, клиентские утилиты и постоянный каталог бекапов.
3. Выполнить `npm run db:migrate`; убедиться в сообщении о проверенной копии.
4. Выполнить `npm run verify:migration:canonical-games`, проверить архив конфликтов
   и запустить новую версию приложения.

При откате восстановить дамп через `pg_restore --exit-on-error` в отдельную
пустую БД с подходящими ролями/правами, проверить данные и переключить прежнюю
версию приложения на восстановленную БД. Не накатывать старый код на новую схему.

## Проверка изменений

Добавлены интеграционные сценарии обновления с историческими результатами,
гостями и JSON-null bye; сохранения канонического Elo и архива конфликтов;
отката при дублях; конкурентной уникальности; отложенной проверки результата;
принадлежности командных ссылок и поведения удаления столов/раундов.
Добавлен unit-сценарий запрета миграции при ошибке бекапа.
Исторические тесты 010/034/035 строят соответствующую прежнюю схему, вместо
повторного запуска несовместимой старой миграции над новой схемой.

Локальные автотесты не запускались по `AGENTS.md`; требуется CI для этого diff.
Docker-образ в этой сессии не собирался. Проверка JavaScript выполнена через `node --check`, diff — через `git diff --check`.

Остающиеся производные данные (`round_number`, `player_ids`, одиночная фракция
рядом с массивом фракций, рейтинговые агрегаты) не удалены: это отдельный переход,
который не нужен для устранения двойного хранения результата. Снимки составов,
профилей и аудит сохраняют историю и не являются альтернативным текущим результатом.

Составные FK с выборочным SET NULL сохраняют ID турнира при удалении стола или
участника; использована [семантика PostgreSQL 16](https://www.postgresql.org/docs/16/ddl-constraints.html).
