# Сервис тирлистов

Редактор `/tierlist` открывается из главного меню и профиля KT Companion.
Карточки распределяются по S, A, B, C и F; оставшиеся находятся в нижнем пуле.
Гость может работать с локальным черновиком. Вход в общий аккаунт позволяет
сохранять тирлисты с названием и выбранным сезоном, открывать их на другом
устройстве, изменять и удалять. Сохранённые тирлисты доступны только владельцу.

## Процесс и данные

`tierlists` — отдельный прикладной процесс с портом по умолчанию `3028`.
Gateway направляет в него `/tierlist/*` и `/api/tierlists/*`.
Внешний адрес, cookie `sid`, шапка и вход остаются общими с Companion.
Перезапуск или недоступность HTTP-процесса tournaments не мешает сохранению
тирлистов. Процесс не обращается к его API и бизнес-таблицам.

Сервис использует ту же PostgreSQL, собственную схему `tierlists` и login-роль
`kt_tierlists`. `tierlist_seasons` хранит каталог сезонов, `saved_tierlists` —
приватные документы. Поля документа: UUID, владелец, название, сезон, JSON
распределения, номер ревизии и время создания/изменения. Индексы поддерживают
выборку по владельцу, сезону и времени изменения.

Общий аккаунт проверяется ограниченными контрактами `accounts.session_identity`
и `accounts.renew_session`. Внешний ключ на `accounts.users` удаляет документы
при удалении аккаунта (`ON DELETE CASCADE`). Это зависимость от общего сервиса
идентификации; турнирные данные для редактора не нужны. Отказ общей PostgreSQL
затрагивает все сервисы, которые хранят в ней данные.

## Миграция и запуск

Миграция `087_tierlists` создаёт схему, две таблицы, индексы и исходный каталог
сезонов. Она выполняется административным подключением, а не прикладной ролью.
Для обновления существующего развёртывания применить стандартную процедуру
[миграции и переключения сервисов](service-separation.md):

1. Добавить в закрытый `.env` случайный `TIERLISTS_DB_PASSWORD` длиной не менее
   24 символов, как для остальных сервисных ролей.
2. Выполнить `npm run db:migrate` с подключением владельца БД.
3. Выполнить `npm run db:provision-services`: это создаст или обновит роль и выдаст
   ей права на новые таблицы и ограниченные общие контракты.
4. Запустить `npm run start:services`, либо отдельно
   `npm run start:service -- tierlists`.

Внутренний порт меняется через `TIERLISTS_PORT`; отдельно запущенный gateway
использует `TIERLISTS_URL`. Для ручного или контейнерного запуска нужны
`SERVICE_NAME=tierlists`, свой `PORT` и `DATABASE_URL` роли `kt_tierlists`.
Прикладная роль не должна получать административную строку подключения.
Compose запускает сервис через `docker-compose.services.yml`, после подготовки
схем и ролей. Логи launcher находятся в `work/tierlists-<port>.*.log`.
`npm start` сохраняет совместимый режим одного процесса.

Проверки доступности: `/health/live` и `/health/ready`; готовность требует
применённую миграцию 087. Через gateway проверить страницу `/tierlist` и публичный
`/api/tierlists/catalog`. С обычной сессией проверить сохранение и повторное
открытие документа. Автоматические проверки выполняются в CI; локальный запуск
полного или выбранного набора тестов не требуется.

## API

Все пути ниже начинаются с `/api/tierlists`. Время возвращается в ISO 8601.

| Метод и путь | Доступ | Результат |
| --- | --- | --- |
| `GET /catalog` | Публичный | `{version, teams:[{id,name,image}]}` |
| `GET /seasons` | Публичный | `{seasons:[{id,label,startsAt,endsAt,isActive}],currentSeasonId}` |
| `GET /` | Владелец | `{tierlists:[summary],accountId,csrfToken}`; необязательный `?seasonId=` |
| `GET /:id` | Владелец | `{tierlist,accountId,csrfToken}` |
| `POST /` | Владелец | Новый документ, ответ `201` с `{tierlist,accountId,csrfToken}` |
| `PATCH /:id` | Владелец | Обновлённый документ с новой ревизией |
| `DELETE /:id` | Владелец | `{deleted:true,accountId,csrfToken}` |

`summary` содержит `id`, `title`, `seasonId`, `revision`, `createdAt`, `updatedAt`.
Полный `tierlist` дополнительно содержит `rows`. Создание принимает:

```json
{
  "title": "Мой тирлист",
  "seasonId": "2026-q3-dataslate",
  "rows": {
    "S": ["angels-of-death"],
    "A": [],
    "B": [],
    "C": [],
    "F": [],
    "pool": []
  }
}
```

Пример сокращён: отсутствующие команды каталога сервер добавляет в конец `pool`.
Обычно клиент отправляет все карточки ровно один раз. Разрешены только указанные
ряды и известные ID команд; дубликаты и неизвестные ID возвращают `400`.
Порядок карточек внутри каждого ряда сохраняется. Название обрезается по краям,
должно занимать одну строку и содержать от 1 до 120 символов.
Неизвестные поля тела запроса отклоняются.

`PATCH` принимает **полный** документ `{title,seasonId,rows,revision}`.
`DELETE` принимает `{revision}`. Начальная ревизия равна 1; при каждом обновлении
она увеличивается. Устаревшая ревизия возвращает `409`: клиент загружает
актуальную версию, а сервер сохраняет более новые изменения. UUID генерируется
сервером, параметр `:id` проверяется до обращения к записи.

На аккаунт разрешено до **100** документов. Создание сверх лимита возвращает
`409`; блокировка в транзакции предотвращает обход параллельными запросами.
Тело POST/PATCH ограничено 32 КиБ, DELETE — 1 КиБ. Общие ограничения частоты
запросов продолжают действовать.

Приватные ответы имеют `Cache-Control: no-store`. Публичные каталог и сезоны
используют `no-cache`. Ошибки: `400` — неверные данные или сезон; `401` — нет
сессии либо аккаунт изменился; `403` — CSRF или источник запроса; `404` — документ
не найден, принадлежит другому аккаунту или UUID некорректен; `409` — конфликт
ревизии или лимит документов.

## Привязка к аккаунту и CSRF

Владельцем всегда становится пользователь текущей серверной сессии. Поле
`userId` из браузера не принимается. Все чтения, изменения и удаления документа
ограничены его владельцем; знание чужого UUID не даёт доступ.

Перед записью клиент получает `accountId` и `csrfToken` через список или
открытие документа. Каждый POST/PATCH/DELETE передаёт:

```text
X-Tierlist-Account: <accountId>
X-CSRF-Token: <csrfToken>
```

Сервер сравнивает аккаунт с текущей сессией, проверяет токен, привязанный к `sid`,
и допустимый Origin. После смены аккаунта или сессии клиент должен обновить
контекст; старый черновик не сохраняется молча от имени другого пользователя.
Токен нельзя переносить между сессиями. Сохранение для гостя недоступно.

## Сезоны: независимый снимок

Каталог принадлежит `tierlists.tierlist_seasons`. Исходная миграция содержит
`2026-q2-dataslate` и `2026-q3-dataslate`, граница между ними —
`2026-09-26T00:00:00+04:00`. Это зафиксированный снимок опубликованных названий
из `public/game-data.js`, а не загрузка турнирного справочника при запуске.
Runtime не читает этот файл, турнирные таблицы или турнирное API сезонов.

`isActive` вычисляется по текущему времени: начало включительно, конец
исключительно; `null` означает открытую границу. `currentSeasonId` выбирает
последний начавшийся активный сезон, с резервным выбором по датам каталога.
В списке остаются и завершённые сезоны: для них можно открыть, исправить и
сохранить исторический тирлист.

Новый dataslate добавляется собственной нумерованной миграцией сервиса:
добавить стабильный `id`, название, даты и позицию, закрыть предыдущий период
при необходимости. Существующие ID не переименовывать и не удалять: документы
ссылаются на них внешним ключом. Обновление турнирного сезона само по себе
не меняет сезон сохранённых тирлистов и не заменяет эту миграцию.

## Каталог и изображения

Рабочий каталог находится в `public/tierlist/catalog.json`: версия, стабильный
ID, отображаемое название и URL PNG. Изображения лежат в
`public/tierlist/images/`. В исходном комплекте 48 карточек с прозрачным фоном,
в том числе одна Spectre и одна Dragon Master Clanblade.

Импортированный архив хранится в
`X:\Vibecoding\Thunderground Tournament System\Kill-Team-Tierlist`:
`transparent/` — исходные PNG, `models.txt` — соответствия ID, PDF-объектов и
источников, `recover.py` — восстановление изображений с альфа-маской.
46 изображений извлечены из PDF правил команд; две дополнительные карточки
импортированы из подготовленных ранее вырезок. Это архив подготовки ассетов,
а не зависимость работающего сервиса.

Ссылки на PDF сохранены или восстанавливаются в `models.txt`/`recover.py`:
[официальный раздел загрузок Kill Team](https://www.warhammer-community.com/en-gb/downloads/kill-team/),
например [PDF Sanctifiers](https://assets.warhammer-community.com/eng_kt_teamrules_sanctifiers-q8qo0bjsrl-dzctvhlcn3.pdf).
Часть записей архива использует адреса PDF CDN. Запуск приложения не скачивает
PDF и не обращается к TierMaker.

При добавлении команды положить PNG и новую запись в каталог, сохраняя
существующие ID. Отсутствующая в старом документе новая карточка появится в пуле.
Удаление или переименование используемого ID требует отдельной миграции
сохранённых документов; без неё старый документ содержит неизвестную карточку.
