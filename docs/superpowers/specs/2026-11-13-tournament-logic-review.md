## F1. Старая форма результата завершает матч с новым соперником

**P2. Код:** `src/api/tournaments.js:2277-2281`; `src/domain/scoring.js:101-104`.

Игрок A открывает форму A–B. Организатор меняет ещё не сыгранные пары на A–C и B–D. Редактор сохраняет ID матча A, но пересоздаёт его canonical game (`tournaments.js:1059-1078`). Старая форма отправляет счёт A/B на прежний URL с ID матча (`public/app.js:7010-7013`); обновление при открытой форме намеренно приостановлено. A остаётся уполномоченным участником A–C. Сервер берёт его старый счёт, подставляет C ноль и игнорирует B, после чего завершает A–C и начисляет Elo.

**Требуемое поведение:** привязать форму к текущей игре; отвергать устаревшую игру с 409. Требовать оба ожидаемых ключа счёта. Явный нулевой счёт допустим, отсутствие стороны недопустимо. Ни результат, ни рейтинг при отказе не меняются.

**Регрессия:** сохранить payload A–B, изменить пары через настоящий API редактора, отправить старый payload как A. Проверить отказ и неизменность всех результатов и рейтингов. Проверить также устаревшую форму после пересоздания игры с теми же сторонами.

## F2. Редактирование после удаления аккаунта меняет ключ и теряет счёт

**P2. Код:** `src/api/tournaments.js:2379-2383`.

Завершить матч текущего Swiss-раунда, удалить аккаунт одной стороны, затем сохранить прежний результат из страницы игры. FK обнуляют `tournament_participants.user_id` и `game_participants.user_id`; сохранённый `game_participants.result_key` остаётся положительным. Страница игры использует этот сохранённый ключ. Обработчик же выводит новый отрицательный ключ из ID турнирного места, а scoring подставляет ноль для отсутствующего ключа. При стандартном `factionCount=1` неизменённый счёт может сохранить ноль вместо результата удалённого игрока, вплоть до смены победителя. Проверка победителя в БД не требует присутствия обоих исходных ключей счёта.

**Требуемое поведение:** идентичность результата брать из записанных `game_participants` и снимков замены. Сохранять `resultKey`, оставлять удалённый `userId` равным null. Одинаковые submitted scores должны сохранять те же счета, фракции и победителя.

**Регрессия:** реальные user IDs отличаются от participant IDs; завершить 21–14, удалить каждую сторону по очереди, отправить тот же результат через `/api/admin/games/:id/result`. Повторить со снимком замены. Имеющийся тест удаления аккаунта проверяет чтение/пересчёт standings, а не обычную запись результата.

## F3. Пересчёт рейтингов создаёт обратный порядок блокировок

**P2. Код:** `src/api/tournaments.js:2232-2233,2259`; `src/api/rating-replay.js:84-87`.

Завершение сначала блокирует свою игру и её пользователей, затем глобальный replay блокирует всех пользователей по ID и все завершённые игры. Две транзакции разных турниров с разными игроками могут удерживать свои user locks и ждать друг друга в replay. Блокировки строк разных турниров этого не предотвращают. Аналогичный цикл возникает между коррекцией игры и явным replay. PostgreSQL прерывает одну транзакцию; router возвращает 503, `withTransaction` повторной попытки не делает.

**Требуемое поведение:** единый протокол блокировок перед блокировкой игр, турнирных строк и пользователей во всех путях изменения рейтингов. Блокировка только внутри replay приобретается слишком поздно.

**Регрессия:** два независимых клиента транзакций одновременно завершают матчи разных турниров; оба коммитятся ровно один раз. Отдельно проверить replay параллельно коррекции. Использовать управляемые барьеры/состояние блокировок, а не задержки `sleep`.

## F4. Bye не участвует в проверке повторного назначения игрока

**P2. Код:** `src/api/tournaments.js:250-252`; `public/app.js:10191-10198`.

При пяти участниках раунд содержит `[bye 5, 1–3, 2–4]`. В редакторе можно заменить 1 на 5: скрытый bye не входит в набор занятых игроков UI. Сервер тоже возвращается из ветки bye до добавления 5 в `seen`, поэтому принимает `[bye 5, 5–3, 2–4]`. Участник получает bye и играет в том же раунде. Ограничения БД проверяют стороны внутри одного матча, но не эту уникальность между матчами.

**Требуемое поведение:** участник bye занимает место в общей проверке всего раунда; его нельзя назначить в другую пару. Не вводить общее требование непустых слотов: пустые обычные слоты уже являются поддерживаемым поведением.

**Регрессия:** API отвергает повтор bye-участника без сохранения черновика/матчей; UI блокирует его в списках обычных пар. Обычный раунд с одним bye принимается.

## F5. Нечётный Swiss-раунд не восстанавливается после Undo

**P2. Код:** `src/api/tournaments.js:2077-2083`; восстановление `1282-1289,1338-1342`.

Undo для `[bye 5, 1–3, 2–4]` сохраняет только `[1–3, 2–4]`. При Resume новый blueprint снова содержит bye в позиции 0, а настройка применяется по исходным индексам. Ветка bye пропускает индекс 0; пара 2–4 применяется в позиции 1 и остаётся в позиции 2. Проверка повторов отклоняет preview ещё до открытия диалога. В следующих нечётных раундах дополнительно не сохраняется выбранный получатель bye.

**Требуемое поведение:** draft сохраняет позиции, bye-получателя, пары, столы, миссию и срок; preview и повторная генерация их восстанавливают. Старые сохранённые drafts должны оставаться читаемыми.

**Регрессия:** пять участников, Undo → preview → regenerate; точное равенство исходных пар, bye, столов и срока. Повторить для следующего нечётного раунда. Существующая интеграционная проверка rollback использует четыре участника.

## F6. Удалённые соперники искажают посев следующего Swiss-раунда

**P2. Код:** `src/domain/tournaments/swiss.js:294-302`.

`buildSwissNextRound` передаёт в `buildStandings` только eligible участников. Исторический удалённый соперник отсутствует в lookup: его VP трактуются как ноль, а заработанные очки исчезают из SoS/Buchholz. Публичная таблица правильно использует полный список, поэтому порядок генерации расходится с показанным порядком.

**Конкретный пример:** By TP, критерий `vp_diff`, сиды A1,E2,B3,F4,C5,D6. Первый раунд A–E, B–F, C–D; победы A 12–10, B 12–8, C 12–8. Удалить E,F. Показанная таблица: B(+4),C(+4),A(+2),D(−4); ожидаются B–C,A–D. Генератор видит A(+12),B(+12),C(+4),D(−4) и после обхода повторной C–D создаёт A–C,B–D.

**Требуемое поведение:** считать standings по полной истории и лишь затем отбирать eligible строки для пары. Удалённый участник учитывается в истории, но не получает нового соперника или bye.

**Регрессия:** этот пример в `test/unit/pairing-mode.test.js`; дополнительные SoS/Buchholz случаи и API-проверка удаления с последующей генерацией.

## F7. Сброс старого WTC/Classic-паринга оставляет последующие раунды

**P2. Код:** `src/api/team-tournaments.js:1477-1480`.

После создания второго раунда администратор с подтверждением может сбросить завершённый паринг первого раунда. Проверка наличия поздних раундов работает только для Doubles. Сброс удаляет старые личные игры и переводит первый раунд в active, сохраняя второй раунд. Если второй завершён, генерация третьего возможна: она проверяет только последний раунд. Публикация блокируется до восстановления незавершённого матча, но более поздние пары уже остаются построенными по отменённым результатам.

**Требуемое поведение:** одинаковый запрет для WTC, Classic и Doubles, как уже сделано в `undoPairing:874-877`. Сначала явно откатываются поздние раунды. Отказ не удаляет игры и не меняет рейтинги/аудит.

**Регрессия:** WTC/Classic с двумя сгенерированными раундами; reset первого возвращает 409 и сохраняет данные. Reset последнего остаётся доступен при требуемом подтверждении. Текущий reset-тест использует один раунд.

## F8. Замена игрока оставляет устаревшие Shield/Sword и пары

**P2. Код:** `src/api/team-tournaments.js:254-266`.

В разрешённом администратору редактировании состава после раскрытия Shield можно заменить выбранного игрока. Старая member row остаётся с `ended_at`, новая получает другой ID; match по-прежнему ссылается на старый ID. При подтверждении второго Sword построение пар использует только активных участников и отклоняет старый Shield. Замена после построения пар аналогично блокирует создание игр: `createPersonalGames:1268-1270` возвращает «A paired player is no longer available». Сохранение состава при этом уже прошло успешно.

**Требуемое поведение:** перед заменой/перестановкой отклонять изменения, затрагивающие выбранные ID незавершённого паринга без созданных личных игр. Вернуть 409 с требованием явного reset до соответствующей стадии. После reset разрешить замену. Снимки уже созданных игр и история предыдущих раундов сохраняются.

**Регрессия:** замена выбранного Shield после раскрытия и участника на стадии environment; отказ оставляет состав и match неизменными. Явный reset → замена → завершение паринга работает. Отдельно сохранить существующее поведение замен для будущих раундов после создания игр.

## Проверенные ограничения и исключённые предположения

- Мутации одного турнира сериализуются его строкой; это защищает лимиты конкурентной регистрации, но не глобальный replay разных турниров.
- Сохранены guards турнирных identity, canonical source uniqueness, истории замен и запрет обычного изменения результатов после появления поздних раундов.
- Unranked влияет на личный MMR, а командный пересчитывается по всем завершённым встречам: это явно описано в `docs/documentation/ru/mmr.md:48` и не включено в дефекты.
- Немедленное завершение личного турнирного матча, ручные кубы, пустые слоты и ручной порядок итоговых мест явно предусмотрены текущим кодом/тестами.
- Минимум четыре активных участника Swiss после снятий оставлен продуктовым вопросом, а не подтверждённой ошибкой.
