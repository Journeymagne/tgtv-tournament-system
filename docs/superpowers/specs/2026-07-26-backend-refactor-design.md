# Рефакторинг бэкенда TGTV Tournament System

Дата: 2026-07-26
Базовый коммит: `d2d60e2`
Статус: утверждено

## Цель

Привести бэкенд к стандартам: модули с одной ответственностью и явными
границами, атомарные операции с данными, честные коды ошибок, покрытие
тестами. Попутно устранить найденные при ревью дефекты целостности данных,
безопасности и корректности.

Фронтенд (`public/app.js`, 4033 строки) в объём работ не входит.

## Исходное состояние

`server.js` — 2021 строка. Один модуль отвечает за загрузку `.env`, конфигурацию,
доменные словари, JSON-хранилище, Postgres-хранилище, маппинг строк, валидацию,
пароли, сессии, Elo, логику challenge-треков, сериализацию ответов, HTTP-роутинг,
отдачу статики и bootstrap процесса. Функция `handleApi` занимает 625 строк.
Тестов нет.

## Найденные проблемы

### A. Целостность данных

**A1. Read-modify-write всей БД на каждый запрос.** `readDb()` загружает в память
все users/sessions/challenges/games/feedback; `writeDb()` в одной транзакции
удаляет отсутствующие строки и делает UPSERT каждой оставшейся
(`server.js:438`). Два параллельных запроса дают потерянное обновление:
одновременное подтверждение двух матчей затирает изменение рейтинга одного из
них. `deleteMissing` способен удалить пользователя, зарегистрировавшегося между
чтением и записью соседнего запроса.

**A2. ID выдаёт приложение,** а не последовательность БД (`db.nextIds.user++`,
`server.js:1439`). Две параллельные регистрации получают один id; `resetSequence`
чинит последовательность задним числом.

**A3. Запись на каждом чтении.** `readPostgresDb` выполняет
`DELETE FROM sessions WHERE expires_at <= NOW()` при каждом чтении, включая
анонимные GET (`server.js:414`).

### B. Безопасность

**B1. Утечка контактов.** `GET /api/users` не требует авторизации, а
`publicUserSummary` возвращает `telegramContact` и `registerNickname`
(`server.js:1515`). Telegram всех игроков доступен анониму. Лидерборду эти поля
не нужны — он рендерит только имя и рейтинг.

**B2. Нет флага `Secure` на session-cookie** (`server.js:1454`). Временный пароль
из `/api/admin/users/:id/reset-password` передаётся тем же каналом.

**B3. Нет ограничения попыток входа,** а `crypto.scryptSync` синхронный
(`server.js:876`) — перебор паролей дополнительно блокирует event loop.

**B4. Обход проверки пути в статике.** `filePath.startsWith(PUBLIC_DIR)`
(`server.js:1338`) пропускает соседний каталог с префиксом `public`. Сейчас не
эксплуатируется, так как таких каталогов нет.

**B5. Нет security-заголовков** (CSP, `X-Content-Type-Options`, `X-Frame-Options`).

### C. Ошибки и наблюдаемость

**C1.** Один `try/catch` на весь `handleApi` (`server.js:1983`) превращает любую
ошибку в `400` с текстом исключения: падение Postgres отдаётся как
`400 "connect ECONNREFUSED"`, `TypeError` в коде — тоже как `400`.

**C2.** Логирования нет ни для запросов, ни для ошибок.

**C3.** Исключение после отправки ответа приводит к попытке записать второй ответ.

### D. Корректность и производительность

**D1.** `POST/PATCH /api/admin/games/:id/result` не проверяет статус игры
(`server.js:1850`) — администратор может завершить отменённую игру и начислить Elo.
Единственный обработчик игр без проверки статуса.

**D2.** `PATCH /api/admin/users/:id` присваивает `isAdmin` до проверки «нельзя
снять права с себя» (`server.js:1958`); применённый в том же запросе `rating`
при этом теряется без сообщения.

**D3. Два несовместимых словаря названий Kill Team.** Проверено скриптом:
в треках присутствуют `Tempestus Aquillons` и `XV26 Stealth Suits`, которых нет в
`KILL_TEAM_OPTIONS`; в `KILL_TEAM_OPTIONS` есть `Tempestus Aquilons` и
`XV26 Stealth Battlesuits`, которых нет ни в одном треке. Ради этого расхождения
существуют две карты алиасов, два разных нормализатора ключа (`normalizeKillTeam`
и `teamKey`) и 14 строк алиасов, добавленных хотфиксом v0.6.

**D4. Раздутые ответы.** `/api/games` отдаёт все завершённые игры с полными
объектами игроков, а `publicUser` включает `avatarData` (до 1 МБ base64) и весь
массив `challengeCredits` (`server.js:1201`). В `/api/users` аватар ограничен
лимитом, в `gameView` — нет.

**D5.** `GET /api/users/search` возвращает `404` с телом ошибки при отсутствии
совпадений (`server.js:1637`). Пустая выборка — это `200` с пустым массивом.

**D6. Мёртвый код:** недостижимая ветка `deduct` внутри `if (teamIndex !== -1)`
(`server.js:778`), лишний поиск игры в `challengeView` (`server.js:1192`),
неиспользуемый параметр `game` в `calculateSubmittedResult`.

**D7. Миграции** — набор `ALTER TABLE ... IF NOT EXISTS`, исполняемых при каждом
старте (`server.js:389`): без версий, без порядка, без отката.

### E. Структура

**E1.** `server.js` — 2021 строка с перечисленными выше зонами ответственности.

**E2.** `handleApi` — 625 строк, цепочка `if` с regex по путям; отдельный
обработчик протестировать нельзя.

**E3.** Словари Kill Team продублированы в `public/app.js` (7 мест) со своей
картой алиасов.

**E4.** Нулевое покрытие тестами, нет тестовой инфраструктуры и скрипта `test`.

## Принятые решения

1. **Хранилище:** SQL-репозитории, только Postgres. JSON-фоллбэк удаляется.
2. **Тесты:** встроенный `node:test` — юниты плюс интеграционные против
   Postgres из `docker-compose`.
3. **Цель деплоя:** только Node-сервер. Serverless удалён в v0.5.
4. **Названия Kill Team:** один канонический словарь плюс миграция уже
   сохранённых данных.
5. **Фронтенд не трогаем.** Дублирование словарей во фронте (E3) остаётся.

## Архитектура

Зависимости направлены в одну сторону: `api → domain → db`. Доменные модули не
знают про HTTP, репозитории не знают про домен, обработчики не пишут SQL.

репозиториев, рядом с единственным потребителем.

### Контракт обработчика

Вместо цепочки `if` — таблица маршрутов:

```js
{ method: "POST", path: "/api/games/:id/result", handler: games.submitResult, auth: "user", tx: true }
```

Обработчик — функция `async ({ params, query, body, user, client }) => body`.
Ожидаемые отказы выбрасывают `HttpError(status, message)`. Роутер разбирает путь,
применяет гард авторизации, при `tx: true` открывает транзакцию и передаёт в неё
`client`, ловит ошибки и сериализует ответ. Обработчик тестируется в отдельности,
без поднятия HTTP.

Поле `auth` принимает значения `"none"`, `"user"`, `"admin"`. Гард выполняется на
том же `client`, что и обработчик.

### Атомарность

Атомарность становится свойством маршрута, а не дисциплины автора. Мутирующий
маршрут открывает транзакцию, читает изменяемые строки с `FOR UPDATE`, проверяет
инварианты и пишет результат. Пример для подтверждения результата: `SELECT * FROM
games WHERE id = $1 FOR UPDATE`, затем проверки, `UPDATE games`, `UPDATE users SET
rating = rating + $delta` для обоих игроков, коммит. Параллельный запрос
блокируется на строке игры и видит обновлённое состояние вместо того, чтобы
затирать его. Функции `readDb`, `writeDb`, `deleteMissing` удаляются (A1).

ID выдаёт `INSERT ... RETURNING id`; `nextIds`, `maxNext` и `resetSequence`
удаляются (A2). Сессия проверяется одним индексированным запросом с условием
`expires_at > NOW()`; просроченные удаляются при логине, а не на каждом
чтении (A3).

### Миграции

Таблица `schema_migrations(version, applied_at)`. Файлы миграций нумерованные,
каждый экспортирует `async up(client)`, применяются по возрастанию версии, каждая
в своей транзакции. Единый механизм на JavaScript, потому что миграция `002`
переписывает JSONB и в чистом SQL выражается плохо.

`001_baseline.js` повторяет текущую схему идемпотентно (`CREATE TABLE IF NOT
EXISTS`, `ADD COLUMN IF NOT EXISTS`) — безопасна и на пустой, и на живой базе.

### Удаление JSON-хранилища

`readJsonDb`, `writeJsonDb`, `ensureJsonDb`, `emptyDb` и
`seedPostgresFromJsonIfEmpty` удаляются. Без `DATABASE_URL` сервер не стартует и
сообщает причину. Для legacy-данных добавляется разовый
`scripts/import-json-db.js`.

## Исправления поведения

### Безопасность

- **B1.** `GET /api/users` отдаёт только `{id, name, avatarData, rating, isAdmin}`.
  `telegramContact` и `registerNickname` остаются в авторизованных
  `/api/users/search`, `/api/users/:id` и админских маршрутах.
- **B2.** Флаг `Secure` на session-cookie, управляется переменной `COOKIE_SECURE`,
  по умолчанию включён при `NODE_ENV=production`.
- **B3.** `crypto.scrypt` через `promisify`. Ограничение попыток по IP на
  `/api/login`, `/api/register`, `/api/setup-admin` и
  `/api/admin/users/:id/reset-password`; счётчик в памяти процесса, без новых
  зависимостей.
- **B4.** Проверка пути через `PUBLIC_DIR + path.sep`.
- **B5.** Заголовки на всех ответах: `X-Content-Type-Options: nosniff`,
  `X-Frame-Options: DENY`, `Referrer-Policy: same-origin` и
  `Content-Security-Policy: default-src 'self'; script-src 'self'; img-src 'self'
  data:; style-src 'self' 'unsafe-inline'; object-src 'none'; frame-ancestors
  'none'`. Директива `img-src data:` нужна для аватаров, `unsafe-inline` — только
  для стилей: инлайновых скриптов и `on*`-обработчиков в `public/` нет,
  инлайновых `style=` — два.

### Ошибки и логи

`HttpError(status, message)` — ожидаемые отказы, отдаются как есть.
`ValidationError` — 400. Всё остальное — 500 со стеком в лог и нейтральным
текстом клиенту (C1). Одна строка лога на запрос (метод, путь, статус,
длительность), отдельная — на ошибку со стеком (C2). Перед записью ответа
проверяется `res.headersSent` (C3).

### Корректность

- **D1.** Админский результат разрешён только для статусов `open`,
  `pending_confirmation` и `completed`; для `cancelled` — 409.
- **D2.** Патч пользователя валидируется целиком до применения.
- **D3.** Канонические имена — `Tempestus Aquilons` и `XV26 Stealth Battlesuits`
  (совпадают с именами файлов логотипов и с картой slug во фронте). Единый реестр
  на бэкенде, одна карта алиасов — только для терпимости к историческому вводу.
  Миграция `002` переписывает `faction` в `games.result` и
  `games.pending_result`, а также `team` в `users.challenge_credits`.
- **D4.** `challengeCredits` убирается из всех публичных представлений: во
  фронтенде поле не используется ни разу. `avatarData` ограничивается лимитом
  везде, а не только в `/api/users`.
- **D5.** Поиск без совпадений возвращает `200 { users: [] }`. Видимое изменение:
  фронт покажет «No players found.» вместо «A user with that name does not
  exist.» Ветка пустого результата в `renderSearchResults` уже существует.
- **D6.** Мёртвый код удаляется.

### Совместимость с фронтендом

Формы ответов остальных эндпоинтов не меняются. Проверено, что канонизация имён
безопасна: файлы логотипов уже названы каноническими именами, а строки
`"Tempestus Aquillons" -> "Tempestus Aquilons.png"` и
`"XV26 Stealth Suits" -> "XV26 Stealth Battlesuits.png"` в `app.js` существуют
исключительно для компенсации серверного расхождения и после миграции просто
перестают использоваться.

## Тестирование

Раннер — встроенный `node:test`, новых зависимостей не добавляется. Добавляются
скрипты `test`, `test:unit`, `test:integration`.

### Юнит-тесты (без БД)

- **elo** — симметрия дельт, ничья, границы рейтингов.
- **scoring** — `primaryBonus` через `ceil`, подсчёт тотала, диапазон 0–6, все
  четыре ветки тайбрейкеров, ошибка при отсутствии победителя roll-off.
- **challenge-progress** — credit и deduct, wildcards, порядок событий, `nextTeam`.
- **validation** — имена, профильные поля, avatar data URL.
- **kill-teams** — каждое каноническое имя нормализуется в себя; исторические
  алиасы приводятся к канону; мусорный ввод отвергается. Отдельно — инвариант
  словаря: множества треков и wildcards являются подмножеством реестра Kill Team.
  Это тот же скрипт, что обнаружил D3; в виде теста расхождение больше не
  проходит в main.

### Интеграционные тесты (Postgres из docker-compose)

Каждый прогон работает в отдельной схеме, создаваемой и удаляемой тестом.

- Сквозной сценарий: регистрация, назначение первого администратора, челлендж,
  accept, submit, confirm — с проверкой рейтингов и Elo в базе.
- **Гонка A1:** два параллельных подтверждения одной игры. Ожидание: второй
  запрос получает 409, Elo применяется ровно один раз. На текущем коде тест
  падает.
- Матрица прав: 401 и 403 по каждому защищённому маршруту.
- Миграции: `001` на пустой и на живой базе; `002` канонизирует `faction` в
  `result` и `pending_result` и `team` в `challenge_credits`; повторный запуск
  `002` ничего не меняет.
- Регресс D1: попытка сохранить результат для отменённой игры возвращает 409.
- Регресс B1: анонимный ответ `/api/users` не содержит `telegramContact`.

## Порядок выката

Каждый шаг оставляет приложение работоспособным.

1. Тестовая инфраструктура и юнит-тесты на текущее поведение — сеть безопасности
   до начала перемещений кода.
2. Каркас: `config`, `http/io`, `router`, `logger`, `static`, плюс исправления
   B4, B5, C1, C2, C3. Маршруты пока делегируют в существующий код.
3. Домен: `kill-teams`, `scoring`, `elo`, `challenge-progress`, `validation`,
   `passwords` — под юнит-тестами.
4. Миграции, репозитории и перевод маршрутов на транзакции группами:
   auth, users, challenges, games, feedback, admin — с интеграционными тестами на
   каждую группу.
5. Удаление JSON-хранилища и остатков `server.js`.
6. Миграция `002` и исправления D1, D2, D4, D5.
7. B2 и B3: cookie `Secure`, асинхронный scrypt, ограничение попыток входа.

## Вне объёма работ

- Рефакторинг `public/app.js` — отдельная задача.
- Устранение дублирования словарей во фронтенде (E3): требует нового эндпоинта и
  правок `app.js`, выбран вариант «только бэкенд».
- Переход на express или fastify, ORM, TypeScript: для проекта такого размера с
  одной зависимостью это накладные расходы без выигрыша.
- Кэширование, очереди, SSE и вебсокеты.

## Риски

- Миграция `002` изменяет исторические данные. Выполняется в транзакции, логирует
  число затронутых строк, покрыта тестом на идемпотентность.
- Ограничение попыток входа хранится в памяти и обнуляется при рестарте. Для
  одного процесса под pm2 это приемлемо.
- Перевод всех маршрутов на транзакции меняет поведение при конкурентных
  запросах: там, где раньше последняя запись побеждала, теперь возможен 409.
  Это и есть исправление A1, но клиентские сценарии стоит проверить вручную
  после шага 4.
